# Offer Catcher 功能升级与前端重构执行计划

日期：2026-09-07。接手执行模型：Luna Max。该文档同时记录本次实施基线；当前代码已完成 S1–S5 的本地交付验收，并完成真实 AI 解析联调。移动设备截图仍需在目标设备补验。

## 1. 结论与范围

当前产品是 Streamlit + Python 的求职辅助原型，具备手动画像、规则岗位匹配、AI 解读、简历分析与优化入口。简历上传代码已经存在，但链路尚未可靠完成。本轮目标是把它升级为可用、清晰、美观的求职工作台。

主流程：**上传简历或手动填写 → 确认资料与求职偏好 → 浏览岗位 → 针对选中岗位分析与对话**。

默认继续使用 Streamlit，复用匹配引擎及现有 AI 配置，重构页面结构、状态管理和组件。不要仅改颜色，也不要同时迁移框架。独立 Web 前端需要额外建设 API、上传会话、流式传输和部署方案；等明确需要复杂编辑、多用户资料库或招聘平台形态时再单独立项。

本轮不包含 OCR、真实岗位抓取、登录账户、数据库、自动投递、简历模板编辑器、模拟面试、模型更换。上传支持文本 PDF / DOCX，扫描件给出明确说明和手动入口。

## 3. 必须处理的问题

| 优先级 | 代码证据 | 用户影响 | 处理方向 |
|---|---|---|---|
| P0 | `app.py:312` 没传 AI 参数；`resume_parser.py:218` 默认转入原文正则分支 | 页面写着 AI 解析，实际主入口未调用 AI | 将默认解析器接入真实服务，显式注入可测试的调用器；不要用未使用的参数充当开关 |
| P0 | 上传成功后无去重判断就调用 `st.rerun()`，上传文件仍在 | 静态代码显示存在反复解析、无法稳定进入审核的风险 | 显式状态机、文件指纹、点击开始解析，杜绝 rerun 自动重试 |
| P0 | 审核确认没有复用手动提交的字段校验，也没有立即切换渲染 | 不完整画像进入匹配，跳转不明确 | 共用校验和提交服务，成功后明确 rerun 至结果页 |
| P0 | `validate_and_fill` 对字段类型校验不足；AI 调用返回错误文案而非错误状态 | 非对象 JSON / 非字符串技能等可能报错，服务失败可能被视为空画像成功 | 建立类型明确的结果和错误契约 |
| P1 | DOCX 仅提取 paragraphs；AI prompt 只保留前 4000 字符 | 表格简历及靠后的项目经历可能遗漏 | 按文档顺序处理段落和表格；处理完整允许范围内的文本，不能静默截断 |
| P1 | 审核技能仅保留词库内项，widget key 固定 | 新技能丢失；换文件可能保留上一份审核值 | 合并词库与识别技能，允许补充；按文档版本初始化编辑状态 |
| P1 | 7 字段覆盖度只扣 5 类缺失；姓名和经历被填默认值 | 覆盖度虚高，未知被包装成已识别 | 用原始识别结果统计，不把默认值算成功 |
| P1 | 返回修改调用 `reset_session` | 已填资料与解析成果丢失 | 保留草稿，返回编辑；资料确认变化后标记旧分析过期 |
| P1 | `_refresh` 仅清空对话 | “换一批推荐”没有换岗位 | 更名为“重新生成解读”；其他岗位用“查看更多” |
| P1 | analysis / optimization 固定使用第一名岗位 | 无法分析用户真正感兴趣的职位 | 增加选中岗位状态，所有后续动作绑定该岗位 |
| P1 | 匹配 prompt 只接收 job，要求模型生成匹配度 | AI 可能给出与引擎冲突的分数及排序 | 给模型完整、可序列化的匹配结果；分数和排名只由程序输出 |
| P1 | 自由对话只发送当前提问，没有画像、岗位和历史 | “那第二个呢”等追问无法可靠承接 | 注入当前资料、可见岗位编号、选中岗位及受限历史 |
| P1 | `call_ai_chat_with_retry` 外层重试，但内层吞掉异常 | 重试逻辑无法有效感知错误 | 建立统一错误类型；限定暂时性错误重试，避免重复输出 |

Streamlit 交互会触发脚本重跑，form 则批量提交字段；上述状态修复应遵循这些机制，而非不断追加 rerun。参考：[执行流](https://docs.streamlit.io/develop/api-reference/execution-flow)、[表单](https://docs.streamlit.io/develop/concepts/architecture/forms)、[Session State](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state)。

## 4. 简历上传与解析设计

### 4.1 状态与交互

`idle → selected → extracting → parsing → review → confirmed`，失败进入 `error`，由用户点击重试或转手动填写。

- 首页默认展示上传区，旁边有“手动填写”和“试用示例”。示例必须标为演示数据。
- 选择文件后显示名称、类型、大小，点击“解析简历”才开始。
- UI 显示实际阶段：“读取文件”“识别信息”“请核对结果”，不伪造百分比和剩余时间。
- 同一会话内用文件内容指纹 + 解析版本识别已解析文档。审核字段编辑、切页面和普通 rerun 不重复请求。
- 更换文件后建立新解析版本，重置这份文档的审核草稿；失败后不展示上一份文档的结果。
- 解析与聊天各自维护运行状态；异常路径可靠复位。结果由状态决定，不能只依赖一个 `processing` 布尔值。
- 本轮草稿仅保证当前会话中的页面往返，不承诺刷新浏览器或重启服务后恢复。

### 4.2 解析契约

保留现有匹配画像字段：name、education、school、major、grad_year、skills、experience、target_position、city。教育和经历本轮继续兼容现有模型，不扩成复杂简历编辑器。

解析结果将业务数据与元信息分开，建议结构：`profile`、`raw_text`、`field_status`、`missing_fields`、`warnings`、`parse_method`、`document_id`。

- `field_status` 使用“已提取 / 待补充 / 已修改”等可解释状态，不展示无依据的模型置信度。
- 缺失信息保留空值；不能将“未识别经历”改写为“没有经历”。
- 城市和目标岗位是求职偏好，由用户确认；不得将现居地自动当作求职城市。
- 严格验证顶层对象、字段类型、技能数组元素和年份；非法字段进入待补充或明确失败，不能导致页面崩溃。
- 技能同时支持词库选择和自定义输入，保留识别的新技能，统一处理大小写去重及中英文分隔符。
- 定义覆盖度为七个提取字段中非空且有效的字段比例；不包括用户新增的求职偏好，不使用兜底文本充数。它是完整度，不是准确率。

### 4.3 文件与 AI 处理

- UI 和服务入口均校验空文件、10MB 上限、类型及文件内容；PDF 沿用最多 3 页，超过说明限制。DOCX 不承诺可靠分页限制。
- PDF 正确释放文档资源，区分损坏、加密、扫描件、文本为空；DOCX 包含段落及表格内容，并约束解压规模。
- 15000 字符上限先保留；在允许长度内送入完整文本。超预算时明确报错或采用可测试的分段合并，禁止静默丢弃尾部。
- AI 调用与 UI 文案分离。缺少配置、鉴权失败、超时、限流、非法结果分别处理。设置有限超时和最大重试；不要让 SDK 重试与业务重试层层叠加。
- 有限正则解析可以作为无 AI 时的备选，但必须标明“基础提取，需手动补充”；零字段提取不能显示成功完成。
- 上传区明确说明：点击解析会将提取文本发送给所配置的 AI 服务。文件默认只在本会话内处理，不新增原始简历落盘或跨用户全局缓存，不在日志中记录简历正文。
- AI 将简历当作待提取的数据，不执行其中指令；不补造学校、技能或经历。

### 4.4 审核与提交

桌面显示原文对照与可编辑资料，窄屏改为原文折叠块加单列资料。手动入口与上传入口复用同一套资料编辑组件和校验。

暂沿用已有必填规则：学历、学校、专业、毕业年份、至少一项技能；姓名和经历选填，求职目标允许“不确定”。界面星号与规则一致。必填不全时逐项标注并保留输入。

确认后保存干净画像、计算岗位排名、选择第一名为默认分析对象并进入工作台。资料发生变化后重算排名，旧 AI 报告标记过期或从当前视图移除，避免继续显示为最新结论。

## 5. 前端设计要求

视觉方向：**安静、清晰、专业的求职工作台**。延续 OC 品牌与深青绿识别色，采用暖白底色、墨色标题、清楚的内容层级和少量状态色。主要辨识点是“简历核对台”和“岗位匹配说明卡”。

### 页面 A：开始

- 紧凑品牌栏与一句主标题：“从你的经历，找到下一份机会”。
- 主区域是明显的拖拽上传面板，格式和限制紧邻操作按钮。
- 次操作“手动填写”“试用示例”，不再让用户先看完整长表单再找到上传入口。
- 下方简短展示“确认资料 → 找到岗位 → 优化表达”，不堆叠营销卡片和虚构统计。

### 页面 B：确认资料

- 顶部步骤提示、当前文件和“更换简历”。
- 桌面采用约 40% 原文 / 60% 编辑区，空间不足时上下排列。
- 资料按“教育背景 / 技能与经历 / 求职偏好”分组。
- 字段缺失同时使用文本和边框提示；显示“已识别 5/7 项，补充后开始匹配”。
- 主操作统一为“确认资料并匹配岗位”。不展示一套手动表单加另一套审核表单。

### 页面 C：岗位工作台

- 顶部为资料摘要和“编辑资料”，避免摘要占满首屏。
- 桌面左侧为岗位卡片清单，右侧为选中岗位详情；宽度约 40% / 60%，工作区上限约 1200px。
- 卡片包含岗位、公司、城市、薪资、匹配分数和一条推荐原因；分数标注为规则匹配参考分，不暗示录用概率。
- 详情显示岗位要求、已覆盖技能、缺口、学历和城市判断；提供“匹配分析”“优化建议”入口。
- AI 区显示当前分析对象；对话不挤占岗位浏览主区域。结果先可用，AI 解释按需生成。
- 现有静态岗位统一显示“内置岗位库”；无来源及更新日期时不要声称岗位实时有效。
- “查看更多岗位”展开现有排序后续结果；“重新生成解读”仅更新解读，命名与行为对应。
- 窄屏使用列表 → 详情的单列切换并提供返回入口，不硬塞两列。

### 统一视觉规范

- 建议色板：背景 `#F6F7F3`、表面 `#FFFFFF`、主文字 `#172A28`、次文字 `#526660`、主色 `#0F766E`、浅强调 `#E8F3EE`。实施时实测对比度。
- 标题 28–36px，分区标题 18–20px，正文 14–16px；中文优先可用的思源黑体 / 苹方 / 微软雅黑回退，不依赖外网字体才能正确显示。
- 统一 4/8/12/16/24/32px 间距，10–14px 圆角，轻边框，重点区域少量阴影。
- 输入控件及主要按钮高度至少 44px。每个阶段只有一个最突出主按钮。
- 减少 emoji 按钮，采用文字与风格统一的图标；状态动画克制并支持减少动态效果。
- 优先 Streamlit 原生容器、主题与稳定组件。避免把分开的 HTML 开闭标签当成真实的跨组件容器；不要通过生成式 CSS 类名堆叠补丁。
- 360、390、768、1440px 宽度均能完成核心流程；无横向溢出、遮挡和不可见按钮；键盘焦点可见，错误不能仅靠颜色。

## 7. 验证清单

### 自动化

- 使用合成的文本 PDF、表格 DOCX；至少覆盖损坏文件、空文件、超限文件、纯图片 PDF、加密 PDF。
- 验证 AI 默认调用发生；通过 mock 注入计数，测试编辑、rerun 和重复点击不额外解析；显式重试才再次请求。
- 测试顶层数组/null、错误字段类型、混合类型技能、模型错误文案、无字段结果和超时。
- 测试 4000 字符之后的有效经历仍被送入解析，并保留词库外技能。
- 测试零识别覆盖度为 0%，默认文本不提高完整度；上传 A 后上传 B 不继承 A 的字段。
- 测试返回修改、统一必填校验、确认进入工作台、选中第二个岗位后的分析上下文。
- 测试追问包含必要画像和受限历史；规则排名和分数由程序保持；重新生成解读不改变岗位排序。
- 无 AI 配置时仍能手动提交并看到规则匹配结果；所有自动测试隔离真实配置与外部服务。
- 新测试必须针对行为与已发现缺陷；不要仅断言组件数量或复制实现逻辑。

### 浏览器与人工验收

- 桌面与手机宽度各完成：上传 → 解析 → 修改识别字段 → 确认 → 选岗 → 分析 → 返回改资料。
- 文件上传若测试框架不支持，必须用浏览器补验，不能仅靠预置 session state 宣称完整上传链路通过。
- 真实 AI 联调使用合成简历，核对七字段与已知答案；记录具体失败字段，不宣称没有样本支持的准确率。
- 至少保存开始页、审核页、岗位详情及一个错误状态截图，手机截图不得以桌面缩略图替代。
